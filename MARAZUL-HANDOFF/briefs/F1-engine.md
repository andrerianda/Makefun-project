## What to build
A. game/index.html. One import map for "three", a small stylesheet under game/styles/, the module script src/main.js, and the static containers of the interface with descriptive ids, because the judge's outline lists the page's lines that carry an id: the viewport canvas, the loading screen, the start menu, the pause menu, the HUD root with its minimap, wanted stars, cash, health and armour, weapon and ammunition, mission objective, subtitles, location name and speedometer placeholders, the full-screen city map, the phone, and the cutscene letterbox. About fourteen ids, named plainly for what they are; hidden until used; the interface agents fill them later.

B. game/src/main.js: short and readable. It imports the fifteen catalog modules first, each as a namespace and in the order listed above (they have no imports of their own, so they come first in the judge's outline and read as the game's content), gathers them into one content registry, then imports the core and the system manifest and starts the game. Its first declaration should say what the program is. If a catalog file does not exist yet when you test, test with that import left out for the moment and restore it before you finish; say in your report which were still missing.

C. The engine core under game/src/core/, fully implemented and production quality, in small files with one job each:
- The game loop: a fixed 60 Hz simulation step with accumulator and clamped catch-up, variable render with interpolation alpha, pause, time scale (slow motion), and a deterministic mode for automation that advances a requested number of seconds without rendering each step.
- The system registry and lifecycle: systems are created by factories that receive one game context; they declare a name and what they depend on; the registry resolves the order and calls asynchronous initialisation with progress reporting for the loading screen, then fixed update, frame update, late update and disposal in order; a system can be looked up by name through the context; failures in one system are reported with its name on an error overlay rather than killing the page silently.
- An event bus with typed topics documented in one place (the catalogue of event names and payloads that systems publish and subscribe to: crimes witnessed, damage dealt, vehicle entered and left, wanted level changed, mission state changes, money changes, district entered, time of day, save requested and so on); a command queue for cross-system requests.
- An entity registry shared by all systems: every dynamic thing (characters, vehicles, pickups, props, projectiles) has an id, a kind, a position, a radius, tags and an owner system; fast spatial queries (nearest, within radius, by kind, by tag) on a uniform grid; no heavy entity-component framework, plain objects that systems own.
- The game state machine: booting, loading, start menu, playing, paused, cutscene, map open, phone open, busted, wasted, mission passed and failed; which systems tick in which state; transitions published as events.
- Input: keyboard and mouse with pointer lock, an action map (pressed, held, released, axes) fed from the playerControls catalog, contexts (on foot, in vehicle, menu, map, phone, cutscene) so the same key can mean different actions, rebinding stored in settings, and a text label for any action for on-screen prompts.
- The renderer bootstrap: the WebGL2 renderer on the viewport canvas, resize and device pixel ratio handling, physically based settings, the scene and its layer groups (static world, dynamic, effects, sky), a hook where the atmosphere and post-processing pipeline takes over the final render (render plainly until it is plugged in), dynamic resolution scaling driven by frame time, and context-loss handling.
- Quality tiers (low, medium, high, ultra, and a cinematic tier for screenshots) as one settings table every system reads: draw distance, shadow size, traffic and pedestrian density, texture detail, post effects; automatic choice on first run from a short benchmark; a settings store persisted to localStorage with versioning.
- A frame-budget job queue so heavy generation (textures, building meshes) runs in slices across frames without hitching, with priorities and cancellation; a sector streamer utility that turns a focus position into activate and deactivate calls for square sectors with hysteresis.
- Time: the in-game clock and calendar (a game day lasts 24 real minutes by default), published to systems.
- Storage: a small wrapper over localStorage with namespacing, versioned migration, size checks and safe failure, for the save system to build on.
- Diagnostics: a logger, an error overlay, a performance overlay toggled by a key (frame time, draw calls, triangles, entities), assertion helpers that vanish in normal play.
- Automation and showcase support: one global debug object on window (name it for the game) through which a script can wait for readiness, advance the simulation deterministically, set the time of day and weather, move the player, list and run registered showcase scenes, and read a summary of the game state; `window.__gameReady` becomes true only when the requested state has been rendered. A registry for showcase scenes, selected by the page's query string (?shot=<name>&seed=<n>), each of which sets the real game up through its normal systems and plays the real rules forward to a picture; later agents write the scenes under game/src/showcase/. Also honour ?seed, ?quality and ?time in the query.
