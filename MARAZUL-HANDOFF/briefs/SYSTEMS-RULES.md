# MARAZUL: rules for every game-system programmer (wave 2)

MARAZUL is an original 3D open-world crime game for desktop browsers (three.js r185, static files, ES modules, no build step), built by a team of agents for the make.fun bounty "gta6-01". The aim is first place. An AI judge compares entries two at a time by four screenshots (the cover shown at 768x480) and an outline of the source (file paths, sizes and first declarations in import order), on: (1) a complete open world shown in the screenshots: a city on foot and by car, traffic and pedestrians, a wanted level with police who respond, missions; (2) depth and fun; (3) feel and polish: camera, HUD with minimap, effects, menus; (4) look and originality: a coherent sun-soaked modern city of its own; (5) structure: files with one clear job, named for what they do. The make.fun team then plays the finalists in desktop Chrome with keyboard and mouse. Almost every rival is a flat 2D top-down game; ours wins by being a real, good-looking, playable 3D city.

## Read first
1. /tmp/marazul/briefs/UPDATE.md, the whole file: the working rules (time box of about thirty minutes, the handoff note, authorship), the state of the project, and the owner's direction on camera and movement, which is binding.
2. docs/CONVENTIONS.md and docs/ARCHITECTURE.md: the contract you build against (lifecycle, context, events and commands, entities, states, input, quality tiers, the debug object and showcase scenes, budgets, the import rule for entry modules) and, in section 13, the work breakdown for your system with its acceptance checks.
3. The documentation of the libraries you wrap: docs/CITY_PLAN.md (city plan), docs/PHYSICS.md (physics), game/src/assets/index.js (models), game/src/render/lighting/atmosphere.js (lights, water, weather), game/src/characters/ (character rig and gait; read its note /tmp/marazul/character-runtime/NOTES.md), game/src/render/textures/ (surfaces and signs; note /tmp/marazul/textures/NOTES.md), game/src/catalog/*.js (all content and ids).

## Rules (break none)
1. Work only inside /home/user/Makefun-project; never `cd` out of it. Never read /home/user/Makefun-project-old, /root/.config or /root/.makefun.
2. Every repository text file is typed with the Write or Edit tool. Never create or change a repository file from the shell (no redirection, heredoc, sed, Python or Node scripts that write); scripts may write only under /tmp/marazul/<your area>/. Nothing downloaded or copied.
3. The game is static files under game/, plays with no network request, imports only relative paths or the bare specifier "three" (and the vendored add-ons through relative paths). Keyboard and mouse only.
4. Write only in the paths your brief gives you. If you need a change in another owner's file, write the request in your report and your note; do not make it. The one exception is game/src/core/systems/gameSystemManifest.js, which you never edit: your system already has its entry module there.
5. Your entry module stays under 6 KB, imports statically only from game/src/core/, and loads its implementation with import() in init() (docs/ARCHITECTURE.md section 1 explains why; tools/tests/core/systemManifest.test.mjs enforces it). Every other file: one clear job, named for what it does, its first declaration its main export with a descriptive name, a few hundred lines at most.
6. Do not run git commands that write, the make.fun CLI, subagents or workflows. Leave no process running when you finish.
7. Check your work in the real game: `node tools/smoke-game.mjs` must pass with no console error when you stop, and look at captures of the game with your system working (`node tools/capture.mjs --size 960x540 --page "index.html?shot=<scene>&seed=1&quality=high" --out /tmp/marazul/<area>/x.jpg`, or drive the page through window.MARAZUL with --eval or --eval-file). The browser renders in software here (seconds per frame); keep captures few and small, JPEG 960x540, and read at most about twenty images per shift. Pure logic gets Node tests under tools/tests/<your area>/.
8. Performance matters for the finalists' play: no allocation per frame in hot paths, pooled objects, budgets from docs/ARCHITECTURE.md section 11.
9. Other systems are being written at the same time as yours. Use only what exists and is documented; where you depend on a system that is still a stub, code against the interface docs/ARCHITECTURE.md gives it and degrade gracefully when it is missing, so the game still boots.

## End of shift
At about thirty minutes: stop at a consistent state (smoke passing, your tests passing), update /tmp/marazul/<your area>/NOTES.md (done, decisions, next steps in order, known problems, commands, requests to other owners), and hand back a short report.
