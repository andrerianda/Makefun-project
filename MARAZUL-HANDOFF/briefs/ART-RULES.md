# MARAZUL: rules for every Blender artist agent

MARAZUL is an original 3D open-world crime game for desktop browsers (three.js r185, static files, no build step), built by a team of specialist agents for the make.fun bounty "gta6-01". The aim is first place. An AI judge compares entries two at a time, mostly by their screenshots (the cover is shown at 768x480, the others smaller), and the make.fun team then plays the finalists in desktop Chrome. Almost every competing entry is a flat 2D top-down game; ours wins on being a real, good-looking 3D city. The owner's direction is explicit: truly 3D and realistic, including the people; modelled in Blender by our own scripts and baked; nothing blocky, toy-like or Minecraft-like. The setting is a fictional sun-soaked Gulf-coast metropolis (pastel stucco, glass towers, palms, beaches, a port, wetlands), seen most often in golden-hour light.

## Rules (break none)
1. Your working directory is the git repository /home/user/Makefun-project. Never `cd` out of it; run every command from it. Never read /home/user/Makefun-project-old, /root/.config, /root/.makefun or any other project's code.
2. Authorship: every source or text file in the repository (Python, JavaScript, HTML, Markdown) is typed by you with the Write and Edit tools. Never create or change repository text files through the shell (no redirection, heredoc, sed, tee, generators, formatters), and never download or copy code, models, textures, HDRIs, fonts or any asset. The art is original: every mesh is built by our Python scripts with Blender's own modelling tools, every texture is baked from materials our scripts define. Blender's built-in procedural nodes, modifiers and primitives are tools and are fine; add-on asset libraries, downloaded packs, bundled demo assets and Blender's built-in font (no text objects) are not.
3. Originality: no real brand, badge, logo, licence plate format or recognisable copy of a specific real product or of anything from a commercial game. Use real-world proportions and construction logic from general knowledge, and design your own shapes. Invented names come from the catalogs under game/src/catalog/ when they exist (a writer agent is producing them now); never invent visible lettering yourself: the game paints lettering at run time.
4. Generated files in the repository are binary only: models as .glb with embedded WebP textures, written by the pipeline under game/assets/<domain>/. Never write generated text formats into the repository (no .gltf, .json, .obj, .mtl, .svg, .csv), and keep every scratch file, preview and cache under /tmp/marazul/<your area>/.
5. Do not run git commands that write; the orchestrator commits. Do not run the make.fun CLI. Do not start subagents or workflows.
6. The pipeline is shared and frozen: do not edit art/blender/lib/**, art/build_assets.py, art/README.md, game/src/assets/*.js, tools/preview/asset-viewer.html or tools/tests/assets/** (an edit under art/blender/lib/ makes every artist's assets stale and can break their builds). Read art/README.md first, then the example art/blender/assets/props/street_lamp_a.py, then the library modules you need. Helpers that several of your assets share go in files whose name starts with an underscore inside your own domain directory (the runner hashes them with your assets and does not treat them as assets). If the library has a real bug or lacks something you need, work around it in your helpers and say so in your report.
7. Write only inside the paths your brief gives you. Other artists are working in the neighbouring domains at the same time.
8. Building and baking run on a rented GPU, which costs money by the hour and switches itself off when idle:
   `/opt/marazul-tools/gpu-run -- /opt/marazul-blender/bin/python art/build_assets.py build <asset_id> --preview`
   Only if gpu-run exits with code 75 (no GPU to be had) run the same command without the `/opt/marazul-tools/gpu-run --` prefix (slow CPU fallback). The first job after an idle period can wait some minutes for the machine. The GPU machine runs two jobs at a time for all artists: build several assets in one command when you can (`build a b c --preview`), do not rebuild what has not changed, and model with quick `preview <id> --source` checks before paying for a full bake. Never leave a loop or watcher running.
9. Look at your own work and iterate: open the Cycles preview sheets (and for a sample of assets the in-engine picture from tools/preview/asset-viewer.html) with the Read tool, compare with how the real thing looks, and keep improving proportions, silhouette, bevels, panel gaps, material response and wear until it reads as a real object at both 768x480 and close up. Review pictures are JPEG 960x540 quality 70; read at most about forty-five images in all (your session is recorded; large images bloat it), so use contact sheets with several views per image.
10. In-engine pictures: only one headless browser may run at a time on this machine; hold an exclusive lock on /tmp/marazul/browser.lock while yours is open. Use tools/capture.mjs if it exists by then (a bootstrap agent is writing it; see docs/CONVENTIONS.md and tools/preview/README.md when present); until then model your scratch script on /tmp/marazul/assets/probe/shot.mjs (copy the approach into your own scratch directory). The browser renders in software here and is slow; a few frames are enough.
11. Budgets are hard: the whole game/ directory must stay under 48 MiB and 993 files and directories in the end, and the page must hold 60 fps on a mid-range desktop GPU with a street full of your assets. Your brief gives your share. Fewer, better files: prefer one .glb with several named variants or parts sharing one atlas over many small files where that is natural.
12. Register every asset you ship by hand in your registry module under game/src/assets/registry/ (the tests in tools/tests/assets/ check registry against files: run `node --test "tools/tests/assets/*.test.mjs"` before you finish and leave it passing). If your brief gives you a new registry module, add its one import line and spread to game/src/assets/registry/index.js with a single small Edit, touching nothing else there.

## Conventions (see art/README.md for the full contract)
- In the game: 1 unit = 1 metre; +Y up; an object's forward is -Z. In Blender you author Z up, facing +Y, right side +X, on Z = 0; the exporter converts.
- Names are the contract with the game: levels of detail (lod0, lod1, lod2 or <part>_lod0...), moving parts, anchors (anchor_*), collision proxies (col_box_*, col_cyl_*, col_sphere_*, col_hull_*, col_mesh_*), and material roles by name prefix: paint* (baked neutral, recoloured at run time, clear coat kept), glass* (not baked, alpha blended), lamp_<group> (emissive, switched per group by the game), cutout* (alpha tested, double sided), tile_<name> (its own repeating texture set), anything else merges into the asset's one baked atlas.
- Light in the game: physically based, ACES-like filmic tone mapping, a low warm sun with long shadows as the signature look, a sky-only environment map. Asphalt albedo is about 0.1; keep base colours physically plausible (no pure white or black, no over-saturated primaries) so assets sit together under one light.

## Report back when done (concise)
The asset list as a table (id, triangles per level, draw calls, texture sizes, bytes); the node, anchor, collider and material names the game code must know; the commands to rebuild; where your preview sheets are (paths under /tmp/marazul/); what you would improve with more time; anything in the pipeline that did not work.
